# 프로젝트 AGENTS 안내

이 문서는 사람이 보기 쉽게 정리한 한국어 참고본입니다.
Codex의 실제 instruction discovery에는 사용되지 않습니다.
실제 적용되는 규칙은 같은 위치의 `AGENTS.md`를 기준으로 합니다.

## 로딩 방식

- 이 작업 공간에서는 `codex/` 디렉터리 자체를 Codex 루트처럼 취급합니다.
- 따라서 기본적으로 `codex/AGENTS.md`를 기준으로 instruction discovery가 이뤄집니다.
- 같은 디렉터리에 `AGENTS.override.md`가 있으면 일반 `AGENTS.md`보다 우선합니다.
- 대체 파일명은 `.codex/config.toml`의 `project_doc_fallback_filenames` 설정을 따릅니다.

## 기본 원칙

- 이 작업 공간의 Codex 규칙은 `codex/AGENTS.md`를 기준으로 관리합니다.
- 변경 범위는 가능한 한 작업에 필요한 최소 수준으로 유지합니다.
- 동작을 바꾸기 전에 현재 코드를 먼저 확인합니다.
- 큰 리팩터링보다 방어 가능한 가장 작은 변경을 우선합니다.
- 최종 요약은 실제 변경점, 리스크, 검증 내용 중심으로 작성합니다.

## 협업

- planner, designer, code mapper, frontend engineer, docs researcher, reviewer, security reviewer, accessibility reviewer, performance reviewer, test engineer는 서로 다른 역할로 다룹니다.
- 소유 경로나 실행 흐름이 불명확하면 구현 전에 `code_mapper`로 실제 코드 경로를 먼저 파악합니다.
- 프레임워크나 API 동작을 공식 문서로 확인해야 할 때는 `docs_researcher`를 사용합니다.
- secret, 인증, 권한, unsafe rendering, 의존성, 민감정보 경계가 바뀌는 경우 `security_reviewer`를 사용합니다.
- 역할 간 핸드오프 시 가정, 리스크, 열린 질문을 분명히 남깁니다.
- 스타일 의견보다 정확성, 회귀, 접근성, 검증 누락을 우선합니다.

## 구현 기준

- 의미 있는 하드코딩 값은 이름 있는 상수로 바꿉니다.
- 축약형보다 의도가 드러나는 이름을 선호합니다.
- 함수는 한 가지 책임에 집중하도록 작게 유지합니다.
- 반복 로직은 복사보다 추출을 우선합니다.
- 작업과 무관한 정리는 하지 않습니다.

## 성능

- 최적화 전에 실제 병목을 먼저 특정하고, 측정되었거나 분명히 예상되는 비용에만 대응합니다.
- 불필요한 O(n^2) 연산을 피하고, 반복 조회에는 `Map`이나 `Set`을 선호합니다.
- 비용이 큰 계산은 렌더 경로 밖으로 빼냅니다.
- 메모이제이션은 측정되었거나 분명히 예상되는 비용을 막을 때만 사용하고, 메모된 서브트리에 넘기는 값의 참조 동일성을 유지합니다.
- 스크롤, 리사이즈, 포인터 이동, 타이핑처럼 빈도가 높은 이벤트는 throttle이나 debounce로 다룹니다.
- 큰 컬렉션에는 페이지네이션, 필터링, 가상화를 우선합니다.
- 서로 독립적인 요청은 병렬로 시작하고, 중복 요청은 제거하며, 오래된 응답은 취소하거나 무시합니다.
- 의존성을 추가하기 전에 번들 영향을 확인하고, 무거운 라우트·다이얼로그·에디터·차트는 동적 import로 분리합니다.
- 비동기 콘텐츠 자리를 미리 확보해 로딩 중 레이아웃이 밀리지 않게 합니다.
- 성능 개선을 주장할 때는 무엇을 어떻게 측정했는지와 전후 수치를 함께 적습니다.

## TypeScript 및 React

- `any`는 도입하지 않습니다.
- `unknown`, 제네릭, 판별 유니언, 타입 가드를 우선합니다.
- `React.FC`는 사용하지 않고 명시적 props 인터페이스를 사용합니다.
- `enum`보다 `as const`와 유니언 타입을 선호합니다.
- 객체 계약은 `interface`, 조합이나 유니언은 `type`을 우선합니다.
- export되는 유틸과 공용 헬퍼에는 반환 타입을 명시합니다.
- 타입 전용 import에는 `import type`을 사용합니다.
- 가드나 안전한 narrowing으로 표현 가능한 경우 무리한 assertion을 피합니다.

## React

- 컴포넌트는 레이아웃, 데이터 연결, 재사용 가능한 UI 동작 중 한 가지 책임에 집중합니다.
- 조건 분기가 많은 거대한 prop 중심 컴포넌트보다 합성(composition)을 선호합니다.
- 실제 호출 지점이 2곳 이상 같은 동작을 필요로 하기 전에는 공용 컴포넌트를 만들지 않습니다.
- 프로젝트에 공용 컴포넌트 컨벤션이 없다면 도메인 전용 컴포넌트는 해당 기능 가까이에 둡니다.
- 새 UI 프리미티브를 만들기 전에 기존 디자인 시스템 프리미티브, 토큰, variant, 인터랙션 패턴을 우선 사용합니다.
- UI 렌더링에 필요한 최소한의 상태만 보관합니다.
- 저렴하고 결정적인 값은 상태로 중복 보관하지 말고 렌더 중에 파생합니다.
- 비동기·다단계 UI 상태에는 판별 유니언을 선호합니다.
- 사용자가 관찰할 수 있는 로딩, 빈, 오류, 성공, disabled, 낙관적 상태는 명시적으로 다룹니다.
- 렌더 중에 파생할 수 있는 값에는 `useEffect`를 사용하지 않습니다.
- effect는 구독, 타이머, 네트워크 호출, 브라우저 API, 명령형 통합 같은 외부 동기화에만 묶습니다.
- 필요한 effect 의존성은 모두 포함하고, 의존성 규칙을 억제하기보다 코드를 재구성합니다.
- 컴포넌트보다 오래 살아남을 수 있는 구독, 타이머, 리스너, 비동기 작업은 정리합니다.
- 순서가 바뀔 수 있는 경우 list key는 배열 인덱스가 아니라 항목 식별자에 묶어 안정적으로 유지합니다.
- 검증, 포매팅, 조건부 UI가 값에 의존하면 controlled 폼 필드를 선호합니다.
- pending 상태 중 중복 제출을 막습니다.
- 비동기 이벤트 실패는 사용자에게 보이는 피드백으로 처리합니다.

## 스타일링

- 색상, 간격, 타이포그래피, radius, 그림자, z-index, 모션, 브레이크포인트는 기존 디자인 토큰을 사용합니다.
- 토큰으로 같은 의도를 표현할 수 있으면 원시 값을 하드코딩하지 않습니다.
- 프로젝트의 기존 스타일링 방식을 따르고 두 번째 방식을 들이지 않습니다.
- 스타일은 해당 컴포넌트 옆에 두고, 상태는 깊은 중첩 선택자 대신 variant나 data 속성으로 표현합니다.
- 명시도를 낮게 유지하고 `!important`와 ID 선택자를 피합니다.
- 다른 컴포넌트의 내부를 파고들어 스타일을 덮어쓰지 않고, variant나 slot을 노출합니다.
- 컴포넌트 경계를 넘어 새어 나가는 margin 대신 레이아웃 컨테이너와 `gap`을 사용합니다.
- 모바일 우선으로 설계하고, 브레이크포인트를 늘리기 전에 유동 사이징을 먼저 쓰며, z-index는 정해진 스케일 안에서 관리합니다.
- `transform`과 `opacity`를 애니메이션하고, 지속 시간은 토큰 스케일을 따르며, `prefers-reduced-motion`을 존중합니다.
- 인터랙션 요소에는 hover, `focus-visible`, active, disabled, loading, selected, error 스타일을 정의합니다.
- 동등하게 잘 보이는 대체 표시 없이 포커스 아웃라인을 제거하지 않습니다.
- 테마 변형, 지원하는 최소 뷰포트, 비정상적으로 긴 콘텐츠에서 확인합니다.

## Feature-Sliced Design (FSD)

- 모듈을 작성하기 전에 어느 레이어에 속하는지 먼저 정합니다.
- 레이어 순서는 `app > pages > widgets > features > entities > shared`이며, 모듈은 자신보다 엄격히 아래에 있는 레이어만 import할 수 있습니다.
- 하위 레이어가 상위 레이어를 import하지 않게 하고, 같은 레이어의 슬라이스끼리 옆으로 import하는 것도 금지합니다.
- 같은 레이어의 슬라이스가 공통 로직을 필요로 하면, 옆으로 import하는 대신 하위 레이어(`shared`, 도메인 로직이면 `entities`)로 내립니다.
- 모든 슬라이스와 세그먼트는 `index.ts` Public API로 노출하고, 다른 슬라이스는 내부 파일이 아니라 Public API를 통해서만 import합니다.
- 슬라이스 내부는 기술적 목적에 따라 `ui`, `model`, `api`, `lib`, `config` 세그먼트로 구성합니다.
- 컴포넌트 전용 상태, 타입, 훅, 헬퍼는 이를 사용하는 코드와 같은 위치에 둡니다.
- 도메인에 종속되지 않으면서 실제 호출 지점이 3곳 이상에서 중복될 때만 `shared`로 추출하고, 재사용되는 도메인 로직은 `entities`를 우선합니다.
- 새 패턴을 도입하기 전에 기존 FSD 컨벤션을 먼저 따르고, 무관한 작업에서 전체 구조를 강제로 재편하지 않습니다.

## 접근성

- 일반 컨테이너보다 시맨틱 엘리먼트를 선호합니다.
- 인터랙션 요소의 키보드 접근성을 유지합니다.
- 아이콘 전용 컨트롤에는 접근 가능한 이름을 제공합니다.
- 의미 있는 이미지에는 적절한 `alt`를 제공합니다.
- 색상만으로 의미를 전달하지 않습니다.
- 보이는 포커스 표시와 예측 가능한 탭 순서를 유지합니다.
- 가능한 경우 네이티브 폼 컨트롤, 레이블, 검증 메시지, disabled 상태를 사용합니다.
- 다이얼로그, 팝오버, 라우팅된 화면, 검증 오류, 비동기 업데이트에서는 포커스를 관리합니다.
- 로딩, 성공, 오류, 상태 변화가 화면에 지속적으로 보이지 않는 경우 보조 기술에 전달되도록 합니다.
- 반응형 레이아웃과 브라우저 확대 상태에서도 텍스트, 컨트롤, 인터랙션 대상이 사용 가능해야 합니다.
- 필수적이지 않은 애니메이션은 reduced motion 설정을 존중합니다.
- 텍스트, 아이콘, 포커스 링, 상태를 전달하는 테두리, 읽을 수 있어야 하는 disabled 콘텐츠의 대비를 확인합니다.
- ARIA를 추가하기 전에 네이티브 HTML 동작을 우선합니다. ARIA가 필요하다면 role, name, state를 정확히 유지합니다.
- 사용자-facing 변경에는 최소한 키보드 탐색과 관련 스크린 리더 기대 동작을 포함한 접근성 검증을 포함합니다.

## 보안

- secret, token, API key, credential, private key, 민감한 사용자 데이터를 코드, 로그, URL, 클라이언트 번들, 문서에 노출하지 않습니다.
- 클라이언트에 의도적으로 노출되는 환경 변수는 public으로 간주하고, 서버 전용 값은 서버 전용 경계 안에 둡니다.
- unsafe HTML injection과 사용자 입력 기반 DOM sink를 피하고, 신뢰할 수 없는 마크업은 렌더링하지 않거나 안전하게 처리합니다.
- 인증, 인가, role, tenant, permission 가정이 바뀌는 경우 명시적으로 드러냅니다.
- 제품 구조상 명확히 필요한 경우가 아니라면 민감한 토큰을 브라우저 storage에 저장하지 않습니다.
- 요청, 응답, 세션, 사용자 관련 민감정보를 로그에 남기지 않습니다.
- 의존성 추가와 package script 변경은 supply-chain, 번들, 보안 영향을 함께 확인합니다.
- 인증, 권한, secret 처리, 외부 입력 파싱, redirect, 다운로드, 업로드, 의존성 경계를 바꿀 때는 보안 검증 내용을 포함합니다.

## 검증

- 변경한 정확한 동작을 검증합니다.
- 버그 수정이나 안정 동작 변경 시 테스트를 추가하거나 갱신합니다.
- 읽기 쉬우면서 경계 조건과 실패 경로를 다루는 테스트를 선호합니다.
- 실제 확인하지 않은 동작을 검증했다고 쓰지 않습니다.
- 최종 응답에는 변경한 파일 경로나 핵심 산출물을 언급합니다.

## 작성 스타일

코드 주석, 문서, 커밋 메시지, PR 설명, UI 문구, 응답 등 모든 문장에 적용합니다. 한글 패턴은 im-not-ai AI 티 분류 체계(https://github.com/epoko77-ai/im-not-ai)를 참고했습니다.

### 원칙

- 의미 불변: 사실, 수치, 고유명사, 직접 인용은 문체를 이유로 바꾸지 않습니다.
- 근거 기반: AI 티로 읽히는 구간만 손보고, 깔끔한 문장은 그대로 둡니다.
- 장르 유지: 커밋 메시지를 에세이로 바꾸지 않고, 티가 사라지면 거기서 멈춥니다.

### 번역투 (A)

- "~를 통해" → "~로", "~에 대해" → "~을", "~에 있어서" → "~에서 / ~할 때".
- "~에서의 / ~로의" 이중 조사는 단순 조사로 풉니다.
- "~되어진다" → "~된다", "가지고 있다" → "있다".
- 영어 대명사를 직역해 "그 / 그녀 / 그것 / 그들"을 반복하지 않습니다.

### 구조·관용구 (C·D)

- "첫째 / 둘째 / 셋째" 같은 기계적 병렬과 과도한 불릿·헤딩을 피합니다.
- "결론적으로", "시사하는 바가 크다", "주목할 만하다", "혁신적인" 같은 AI 관용구를 삭제합니다.
- 연결어미 뒤에 불필요한 쉼표를 넣지 않습니다.

### 리듬·수식·완곡 (E·F·G)

- 같은 종결어미를 연달아 반복하지 않고 문장 길이에 변화를 줍니다.
- "매우 / 정말" 같은 강조어와 동의어 이중 수식을 줄입니다.
- "~할 수 있을 것으로 보인다" → "~한다 / ~할 수 있다"로 완곡 표현을 다듬습니다.

### 접속사·형식명사·장식 (H·I·J)

- 문두 접속사("또한 / 따라서 / 즉 / 나아가")를 연달아 쓰지 않습니다.
- "~하는 것이다" → "~한다", "~할 필요가 있다" → "~해야 한다", 불필요한 "점 / 수 / 바"를 줄입니다.
- 과도한 볼드, "따옴표" 강조, 대시(—) 남발, 이모지를 자제합니다.

### 영어 문장

- em 대시(—)나 en 대시(–)를 문장 부호로 쓰지 않고 쉼표, 괄호, 콜론, 문장 분리로 표현합니다.
- seamless, robust, powerful, leverage, delve 같은 과장 표현을 피하고 "활용하다"보다 "쓰다"를 선호합니다.
- "It's worth noting", "In conclusion" 같은 빈 도입/마무리와 "not just X, but Y" 구문을 뺍니다.

### 윤문 대상 제외

- 수치, 단위, 날짜.
- 고유명사, 인명, 제품명, 모델명.
- 큰따옴표 안의 직접 인용, 법률·규정 조문, 불가피한 학술 개념어.
- AI나 언어 모델이라는 메타 언급은 애초에 넣지 않습니다.
